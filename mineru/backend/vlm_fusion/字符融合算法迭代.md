# 字符融合算法迭代记录

本文档用于记录 native 文本与 VLM 文本互相融合的算法迭代。它和 `字符对齐设计.md` 分工不同：

- `字符对齐设计.md` 记录总体背景、约束、原则和待确认问题。
- 本文档记录每一轮具体算法方案，便于持续讨论、修正和收敛。

## 迭代 1：bbox 独立的候选生成 + 字符级裁判 + 保守合并

### 总体思路

融合算法不应简单判断“native 和 VLM 谁更可信”，而应在每个 VLM block / bbox 内独立执行：

```text
VLM block / bbox
    ↓
匹配该 bbox 内 native spans
    ↓
生成多个 native 候选文本
    ↓
native 候选与 VLM 文本做字符级对齐
    ↓
判断 native 是否可用、是否需要按 VLM 重排、是否可补漏
    ↓
输出最终文本 + debug 决策
```

核心目标：

```text
native 提供可信字符
VLM 提供阅读顺序和缺字提示
字符级对齐器负责判断差异类型
融合层按 bbox 做保守决策
```

## 模块拆分

### 1. 预处理层

不要直接拿原始字符串做比较，应先把字符转换成轻量 token：

```python
CharToken(
    raw="，",
    normalized=",",
    char_type="PUNCT",
    index=12,
)
```

`normalized` 只用于比较，不用于最终输出。最终输出应优先使用 native 的 `raw` 字符。

建议归一化内容：

- 全角半角。
- 大小写。
- 常见中英文标点。
- 连续空白。
- 不可见控制字符。

字符分类建议至少包含：

```text
LETTER_OR_CJK
DIGIT
PUNCT
SPACE
MATH_SYMBOL
CURRENCY_SYMBOL
UNIT_SYMBOL
BRACKET_QUOTE
LIST_MARKER
CONTROL_OR_UNKNOWN
```

### 2. 候选生成层

同一个 bbox 内，不只生成一个 native 文本，而是生成多个候选：

```text
native_geo_text
当前按 bbox 几何顺序拼出来的 native 文本。

native_vlm_span_order_text
按 VLM 文本锚点重新排列 span 后的 native 文本。

native_original_order_text
PDF 抽取原始顺序，作为辅助候选。
```

每个候选都要和 `vlm_text` 做字符级对齐，然后选择最可靠的 native 候选作为基础文本。

选择 VLM-guided 顺序必须满足门槛：

```text
anchor_coverage 足够高
conflict_ratio 不高
相比 native_geo_text 的 score gain 明显
```

否则保持当前 native 几何顺序，避免被 VLM 错误牵引。

### 3. 字符级对齐层

核心函数不应只返回 similarity，而应返回结构化对齐结果：

```python
AlignmentResult(
    score=0.86,
    anchor_coverage=0.78,
    conflict_ratio=0.06,
    native_missing_count=2,
    native_extra_count=1,
    vlm_extra_count=3,
    ops=[...],
)
```

对齐操作类型：

```text
MATCH              native 与 VLM 完全一致
EQUIVALENT         归一化后等价
NATIVE_MISSING     native 疑似漏字，VLM 有额外字符
NATIVE_EXTRA       native 有字符，VLM 没有
VLM_EXTRA_OR_ERROR VLM 多识别或误识别
CONFLICT           native 与 VLM 字符不同
```

对齐成本需要按字符类型加权：

```text
普通文字 match：低成本
标点/空白差异：低成本
普通文字缺失：中成本
数字缺失：高成本
公式/代码符号缺失：更高成本
普通文字冲突：高成本
数字/代码/公式冲突：极高成本
```

这样算法会自然倾向于：

```text
普通正文允许少量保守补漏
数字、公式、代码区域极保守
VLM 错字不覆盖 native
```

### 4. 合并决策层

最终合并规则应保守：

```text
native 不可读：
    fallback VLM

native 可读，VLM 为空：
    使用 native

native 可读，VLM 有内容：
    做字符级对齐

    如果 native 顺序明显错，且 VLM-guided native 明显更好：
        使用重排后的 native

    如果 native 少量漏字，且 VLM 缺字位置有稳定前后锚点：
        使用 native + VLM 补漏

    如果 native/VLM 是字符冲突：
        保留 native，不用 VLM 替换

    如果 VLM 多识别：
        丢弃 VLM 多余字符

    如果冲突太多：
        不做重排/补漏，保守使用 native 或 fallback VLM
```

伪代码：

```python
def fuse_text_for_bbox(native_spans, vlm_text, block_type, config):
    if should_skip_alignment(block_type):
        return default_block_strategy()

    native_candidates = build_native_candidates(native_spans, vlm_text)
    best = choose_best_native_candidate(native_candidates, vlm_text, config)

    if not best.native_readable:
        return use_vlm(reason="native_unreadable")

    if not vlm_text.strip():
        return use_native(best.text, reason="vlm_empty")

    alignment = align_native_with_vlm(best.text, vlm_text, config)

    if alignment.too_conflicted:
        return use_native(best.text, reason="conflict_keep_native")

    merged = merge_by_alignment(best.text, vlm_text, alignment, config)

    return use_native_guided(
        merged.text,
        reason=merged.decision,
        debug=alignment.to_debug(),
    )
```

## 第一版建议范围

第一版不要一次做得过激。建议先实现最稳的闭环：

```text
支持普通正文字符级对齐
支持 span 级 VLM-guided 重排
支持少量普通文字补漏
冲突默认保留 native
数字、代码、公式、表格先保守跳过或降低补字权限
每个 bbox 独立判断
```

暂不默认启用的能力：

```text
span 内字符级重排
VLM 替换 native 冲突字符
连续数字自动补漏
代码/公式自动补漏
表格整表普通文本重排
```

## 当前关键判断

本轮算法的重点不是“补得尽可能多”，而是：

```text
VLM 可以指导 native 的顺序
VLM 可以提示 native 漏字
VLM 不应该随便改 native 的字
VLM 不应该随便补数字、公式、代码符号
每个 bbox 必须独立判断
```

## 下一轮需要继续讨论的问题

- `anchor_coverage` 应如何计算，是按字符数、span 数，还是有效 token 数。
- `score_gain` 的初始阈值设置多少合适。
- `native_missing` 连续补字最多允许几个字符。
- 是否要求补字必须落在 native gap bbox 附近。
- 普通正文、列表、图注、页眉页脚是否使用不同阈值。
- block 顺序是否默认参考 VLM，还是先保留当前几何排序。
- 对齐器是否要支持字符类别可插拔，以便后续针对数学、代码、表格扩展。
