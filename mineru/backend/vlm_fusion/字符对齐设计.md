# 字符级对齐与融合设计草案

本文档记录 `vlm_fusion` 中“PDF 原生文本 native 与 VLM 文本如何协同”的讨论结论。目标是在开始写代码前，把问题边界、决策原则、算法方向和待确认点先沉淀清楚，后续可以持续补充。

## 背景

当前 `vlm_fusion` 的核心思路是：

- VLM 负责页面布局、视觉文本和结构化区域识别。
- PDF 原生文本负责提供可复制文本，优先用于普通文本块。
- gap 识别负责在 native span 之间发现可疑空隙，并裁切小图交给 VLM 补字。

现有问题是：PDF native 文本有时内容字符更可靠，但读取顺序可能错误；VLM 的阅读顺序通常更好，但可能 OCR 错字、漏字或多识别。

因此不能简单地选择“native 或 VLM 之一”，而需要更细的字符级融合策略。

## native 与 VLM 的优势劣势

这一节用于明确后续融合时“信任谁的什么能力”。核心结论是：native 和 VLM 都不是整体可信或整体不可信，而是在不同维度上有不同优势。

### PDF native 的优势

PDF native 文本来自 PDF 内置文本层，不经过视觉识别。它在以下方面通常更可靠：

- 字符本身更精确。只要 PDF 文本层正常，native 不会把 `气` OCR 成 `汽`，也不容易把 `0` 识别成 `O`。
- 可复制性更好。native 更接近用户复制 PDF 文本时能得到的字符。
- 普通正文里的中文、英文、数字通常比 VLM 更少错字。
- 标点、大小写、数字、专业术语、变量名等细节通常更可信。
- 对低清晰度、扫描噪声、字体复杂、图片压缩等视觉问题不敏感。
- 成本低，不需要额外模型调用。
- 在可读文本层中，长段文字的字符覆盖率通常较高。

### PDF native 的劣势

native 的问题主要来自 PDF 文本层本身，而不是 OCR：

- 读取顺序可能错误。PDF 内部对象顺序、bbox、绘制顺序不一定等于阅读顺序。
- 多栏、跨栏、页眉页脚、脚注、公式旁注、浮动图文等复杂排版容易顺序错。
- 同一页不同 bbox 的 native 质量可能完全不同，不能整页统一判断。
- 某些 bbox 中 native 为空，因为文字是图片化、轮廓化或矢量化的。
- 可能漏字，尤其是图片化字符、特殊字体、异常编码、嵌入子集字体或不可映射字符。
- 可能出现乱码、控制字符、replacement character。
- span 切分可能很碎，甚至一个词、一个字、一个符号被拆成多个 span。
- span 的 bbox 可能不准确，导致行内排序或 block 匹配错误。
- 单个 span 内部字符也可能已经乱序，这种情况仅靠 span 重排无法修复。
- 表格、公式、脚注、列表编号等区域可能与正文混在一起，缺少语义结构。

### VLM 的优势

VLM 通过页面图像理解内容，因此在视觉阅读和结构判断上有优势：

- 阅读顺序通常更接近人眼，尤其在多栏、图文混排、跨栏标题等场景。
- 能识别图片化文字、扫描文字、截图文字等 native 为空的内容。
- 能提供 layout block，帮助按 bbox 对页面分区。
- 能发现表格、图片、公式、代码等结构化区域。
- 能补充 native 没覆盖到的视觉文字，例如图中文字、图注、页眉页脚。
- 对 native 文本层顺序错的问题，可以提供排序参考。
- 对 native 局部漏字的问题，可以提供候选补字。
- 对复杂排版中“哪一块属于同一段”的判断可能优于纯几何排序。

### VLM 的劣势

VLM 的问题主要来自视觉识别和生成式输出：

- 可能 OCR 错字，尤其是形近字、低清晰度小字、特殊字体。
- 数字、金额、页码、公式符号、变量名、单位等精确字符可能识别错。
- 可能把 `0/O`、`1/I/l`、`5/S` 等混淆。
- 可能漏字、吞标点、改写标点或加入不存在的空格。
- 可能多识别，把边缘字符、相邻 block 内容或装饰性符号读进去。
- 可能规范化文本，例如自动改大小写、简繁、全角半角、标点样式。
- 可能对短文本、页码、脚注编号等上下文弱的区域产生不稳定结果。
- 可能把结构信息和正文混在一起，例如列表符号、表格单元格边界、公式符号。
- 模型输出不一定逐字符忠实，可能有语言模型纠错或补全倾向。
- 成本更高，速度更慢，并且受模型版本和 prompt 影响。

### 应信任的维度

融合时不应问“native 和 VLM 谁更可信”，而应拆成维度：

```text
字符精确性：优先 native
阅读顺序：优先参考 VLM，但需要 native 锚点验证
结构分区：优先参考 VLM layout
图片化文字：优先 VLM
普通正文可复制文本：优先 native
数字、代码、公式符号：native 冲突时优先 native，VLM 补入要极保守
缺字候选：VLM 可以提示，但必须通过字符级对齐和锚点确认
bbox 独立质量：每个 block / bbox 单独判断，不能整页一刀切
```

### 推荐融合心智模型

可以把 native 和 VLM 的角色理解为：

```text
native 是字符仓库
VLM 是视觉阅读顺序和缺失提示
字符级对齐器是裁判
fusion 决策层负责按 bbox 选择策略
```

也就是说，最终输出不应该简单等于 native 或 VLM，而应该是：

```text
VLM 定位 block 和阅读顺序
native 提供可信字符
字符级对齐判断冲突、漏字、误识别和顺序错
在每个 bbox 内独立生成最保守可信的文本
```

## 目标

总体目标：

```text
内容尽量选 native，顺序参考 VLM，漏字谨慎从 VLM 补，不用 VLM 错字覆盖 native。
```

更具体地说：

- native 字符正常且顺序正确时，直接使用 native。
- native 字符正常但顺序错误时，参考 VLM 顺序重排 native。
- native 明确漏少量字符时，可以从 VLM 保守补入。
- native 与 VLM 字符冲突时，默认保留 native，不让 VLM 替换 native。
- VLM 多识别、错识别或不稳定时，不污染 native 输出。
- 判断粒度必须落到每个 VLM block / bbox，而不能按整页统一判断。某些 PDF 同一页里可能部分区域 native 可读，部分区域 native 不可读、漏字或顺序错误。
- 所有关键决策要可观测，debug 模式下记录对齐指标和决策原因。

## 需要区分的问题类型

### block 顺序错误

现有 `fuse_page()` 以 VLM block 为主遍历，但最后会调用 `_sort_fused_blocks()` 按几何位置重新排序。

如果 VLM 的 block 顺序是正确的，而几何排序把双栏、跨栏、脚注或特殊排版排错，就需要允许最终 block 顺序参考 VLM。

### block 内 span 顺序错误

当前 `join_native_spans()` 会按 bbox 把 native spans 聚成行并拼接。

如果 PDF 的 span bbox 或几何顺序不可靠，会出现同一文本块内部顺序错。此时应该尝试用 VLM 文本作为顺序参考，对 native spans 重新排序。

### span 内字符顺序错误

如果单个 native span 内部字符本身已经乱序，仅靠 span 级重排无法修复。

这个场景更危险，因为修复会接近“用 VLM 改写 native 文本”。初期建议只记录和识别，不默认做激进字符级重排。

### native 漏字

native 可能缺少图片化字符、异常编码字符或被 PDF 文本层漏掉的字符。

如果 VLM 在稳定上下文中多出少量字符，并且前后有可靠对齐锚点，可以把它判定为 native missing，谨慎补入。

### VLM 错字

VLM 可能把视觉上相近的字符识别错，例如中文形近字、数字字母混淆、标点错误等。

如果 native 和 VLM 在同一位置出现不同字符，默认视为 conflict，保留 native，不用 VLM 替换。

## 当前实现中的不足

当前 native 是否可靠主要由 `score_native_text_quality()` 判断。它关注控制字符、乱码字符和 replacement character。

这意味着：

```text
native 文本字符干净但顺序错误
=> quality 仍可能很高
=> reliable = True
=> fusion 使用 pdf_native
=> VLM 顺序不会被采用
```

当前 `fusion.py` 中虽然会计算 `text_similarity(native_match.content, vlm_content)`，但只记录 `source_conflict_count`，不会改变决策。

因此需要新增更严格的字符级对齐结果，而不是只返回一个相似度。

## 设计原则

### 每个 bbox 独立判断

不能因为某一页整体 native 文本存在问题，就整页禁用 native；也不能因为某一页大部分 native 可读，就默认所有 bbox 都使用 native。

每个 VLM block 的 bbox 都需要独立完成：

```text
匹配 native spans
评估 native 文本质量
与该 block 的 VLM 文本做字符级对齐
判断是否使用 native、VLM-guided native、native + VLM 补漏，或 fallback VLM
```

原因是同一页中可能同时存在：

- 普通 PDF 文字层，native 完全可用。
- 图片化文字，native 为空，需要 VLM。
- 异常编码文字，native 有乱码，需要 VLM。
- native 字符正确但 span 顺序错误，需要参考 VLM 重排。
- native 局部漏字，需要 VLM 保守补漏。

### native 优先提供字符

只要 native 字符本身可信，输出字符应优先来自 native。

### VLM 优先提供顺序线索

VLM 的主要价值是阅读顺序、视觉缺字提示和 block 结构，而不是直接覆盖 native 文本。

### 冲突时保守

native 与 VLM 字符不同，不等价于 native 错。默认保留 native，并记录冲突。

### 补字必须有锚点

只有 VLM 多出的字符被稳定 native 上下文夹住，才考虑补入。

### 所有策略可配置

新能力应通过配置开关和阈值控制，方便不同 PDF 类型调试。

## 字符级对齐函数

建议新增函数：

```python
align_native_with_vlm(native_text: str, vlm_text: str) -> AlignmentResult
```

它不只是计算相似度，而是做字符级动态规划对齐，并输出结构化结果。

### 对齐成本

可以基于 Needleman-Wunsch 或加权 edit distance：

```text
相同字符：0
归一化等价字符：低成本
空白差异：低成本
native 缺字，VLM 有字：中等成本
native 有字，VLM 没有：中等成本
native 与 VLM 字符冲突：高成本
```

归一化等价可包括：

- 全角半角等价。
- 大小写等价。
- 常见中英文标点等价。
- 连续空白等价。

### 操作类型

对齐后每个差异应被分类：

```text
MATCH              native 与 VLM 完全一致
EQUIVALENT         归一化后一致
NATIVE_MISSING     native 疑似漏字，VLM 有额外字符
VLM_EXTRA_OR_ERROR VLM 疑似多识别或误识别
NATIVE_EXTRA       native 有字符，VLM 没有
CONFLICT           native 与 VLM 字符不同
```

### 返回结构

建议返回结构化对象，而不是单个 float：

```python
@dataclass
class AlignmentResult:
    merged_text: str
    score: float
    anchor_coverage: float
    conflict_ratio: float
    native_missing_count: int
    native_extra_count: int
    vlm_extra_count: int
    operations: list[AlignmentOp]
```

`operations` 在 debug 模式下可以写入 `_fusion`，便于定位具体差异。

## 合并规则

字符合并建议遵循：

```text
MATCH / EQUIVALENT:
    输出 native 原字符

CONFLICT:
    输出 native 原字符
    记录 conflict，不用 VLM 替换

NATIVE_MISSING:
    满足严格条件时才插入 VLM 字符
    否则不插入，只记录疑似漏字

VLM_EXTRA_OR_ERROR:
    默认丢弃 VLM 字符

NATIVE_EXTRA:
    默认保留 native 字符
```

`NATIVE_MISSING` 的建议条件：

- 缺失片段长度较短。
- 前后都有稳定匹配锚点。
- 插入字符不是明显噪声。
- 插入后整体对齐分数提升。
- 如果能落在已检测到的 native gap 附近，置信度更高。

## 符号与非普通文字处理

字符级对齐不能只按“中文/英文正文”处理。PDF 中常见的符号、数字、列表标记、公式、代码、脚注编号等都需要单独约束，否则容易把 VLM 的视觉噪声误补进 native。

### 字符类别

对齐前建议先给字符做轻量分类：

```text
LETTER_OR_CJK       中文、英文、其他普通字母
DIGIT               数字
PUNCT               标点
SPACE               空白
MATH_SYMBOL         数学符号
CURRENCY_SYMBOL     货币符号
UNIT_SYMBOL         单位或特殊符号
BRACKET_QUOTE       括号、引号
LIST_MARKER         项目符号、编号符号
CONTROL_OR_UNKNOWN  控制字符、replacement character、不可见异常字符
```

分类的作用不是改变输出，而是影响对齐成本和补字策略。

### 标点和空白

标点、空白要保守处理：

- 全角半角标点可视为等价，例如 `，` 和 `,`。
- 中文/英文引号、括号可视为近似等价。
- 连续空白、换行和普通空格通常低成本对齐。
- VLM 多出的首尾标点默认不补入。
- native 与 VLM 标点冲突时，默认保留 native。
- 不要因为标点差异触发大范围重排。

### 数字

数字比普通文字更敏感，尤其在金额、编号、页码、年份、公式、表格附近。

建议规则：

- native 和 VLM 数字冲突时，默认保留 native。
- 不使用 VLM 替换 native 数字。
- VLM 补数字必须比普通文字更严格，需要前后稳定锚点。
- 连续数字缺失时默认不自动补，除非后续有明确 bbox gap 或人工确认策略。

原因是 VLM 常见 `0/O`、`1/I/l`、`5/S` 等混淆，数字错一个会造成严重语义错误。

### 数学符号、公式和单位

数学符号、公式和单位不适合用普通正文策略处理。

建议规则：

- 对 `equation`、`formula` 等结构化 block，默认不做 native/VLM 字符级混合，保留现有结构块策略。
- 普通文本中的少量单位符号可以参与对齐，例如 `%`、`℃`、`kg`、`m²`。
- VLM 多出的数学符号默认不补入，除非被 native gap 和稳定上下文同时支持。
- 上标、下标、希腊字母、箭头、积分号等符号冲突时默认保留 native，并记录 conflict。

### 代码和命令

代码、命令、路径、变量名对字符精度要求很高。

建议规则：

- `code`、`algorithm` 等结构化 block 默认不做字符级补字和重排。
- 如果普通文本中检测到明显代码片段，例如包含大量 `{}`, `[]`, `;`, `=`, `_`, `/`, `\`，则降低 VLM 补字权限。
- native/VLM 在代码符号上冲突时保留 native。
- 不用 VLM 自动替换大小写，因为代码大小写可能有意义。

### 列表编号和项目符号

列表区域中常见 `1.`、`(1)`、`a)`、`•`、`-` 等。

建议规则：

- VLM 多出的列表符号不一定补入，因为它可能来自视觉布局而不是正文内容。
- native 缺少列表编号时，可以记录 `NATIVE_MISSING`，但默认是否补入需要配置控制。
- 列表符号不应作为强锚点单独触发大范围重排。
- 如果列表编号后面正文锚点稳定，可以允许 block 内局部顺序参考 VLM。

### 页眉、页脚、页码和脚注编号

页眉、页脚、页码、脚注编号通常短、重复、上下文弱。

建议规则：

- 短文本 bbox 的字符级补字要更保守。
- 页码、脚注编号数字冲突时保留 native。
- VLM 多识别的页眉页脚内容不应因为相似度低就污染正文。
- 这类 block 更依赖 bbox 独立判断，不能把它们的对齐结果扩散到整页。

### 表格

表格内文字和数字位置强相关，普通行文重排可能破坏单元格语义。

建议规则：

- `table` 结构化 block 默认不做字符级 native/VLM 混合。
- 如果后续要支持表格内文字融合，应以单元格 bbox 为最小判断粒度，而不是整张表。
- 表格里的数字和符号冲突默认保留 native 或保留 VLM 结构，不做自动混合。

### 图片、图注和图中文字

图片主体不应参与普通文字对齐。

建议规则：

- `image`、`chart` 等结构块保留 VLM 结构。
- `image_caption`、`table_caption` 可以作为文本 block 参与对齐。
- 图片内部视觉文字如果 native 不覆盖，继续走 `visual_supplement`，不要强行并入附近 native 正文。

### 异常字符与控制字符

native 中出现控制字符、replacement character 或不可见异常字符时，应降低 native 质量。

建议规则：

- `\ufffd`、控制字符、明显乱码片段计入 native quality 惩罚。
- 如果异常字符落在短 bbox 中，整个 bbox 更倾向 fallback VLM。
- 如果异常字符只占少量位置，可保留 native 其他字符，并把异常位置作为潜在 missing/conflict 记录。

### 对齐成本建议

不同类别的对齐成本应不同：

```text
普通文字相同：最低
标点等价：低
空白差异：低
普通文字 native missing：中
标点 native missing：高，默认不补
数字 native missing：高，需要强锚点
数学/代码符号 native missing：更高，默认不补
普通文字 conflict：高，保留 native
数字/代码/公式 conflict：很高，保留 native并记录
```

这样可以让算法在普通正文里灵活，在数字、公式、代码和符号密集区域更保守。

## span 顺序参考 VLM

建议新增：

```python
join_native_spans_by_vlm(spans: list[NativeSpan], vlm_text: str) -> NativeOrderResult
```

候选文本：

```text
native_geo_text        当前按 bbox 拼接的 native 文本
native_vlm_order_text  按 VLM 对齐锚点重排后的 native 文本
```

决策：

```text
如果 native_vlm_order_text 与 VLM 的对齐结果明显优于 native_geo_text
并且 conflict_ratio 不高
并且 anchor_coverage 足够高
=> 使用 native_vlm_order_text
否则
=> 使用 native_geo_text
```

建议初始阈值：

```python
native_vlm_order_min_anchor_coverage = 0.70
native_vlm_order_max_conflict_ratio = 0.25
native_vlm_order_min_score_gain = 0.12
```

## block 顺序参考 VLM

建议新增配置：

```python
fusion_block_order_reference = "vlm"  # vlm / geometry
```

如果为 `vlm`：

- VLM 派生出的 fused block 保留 VLM 输出顺序。
- 不再对这些 block 强制按 bbox 重排。
- `pdf_native_recovered` 这类无 VLM 对应的 block 可按几何位置插入，或者放到相邻位置不明确时的末尾。

如果为 `geometry`：

- 保持当前 `_sort_fused_blocks()` 行为。

## 示例

### VLM 错字，不替换 native

```text
native: 今天天汽很好
vlm:    今天天气很好
```

`汽/气` 属于 `CONFLICT`。默认输出：

```text
今天天汽很好
```

原因：无法仅凭 VLM 判断 native 一定错，不能让 VLM 错字覆盖 native。

### native 漏字，VLM 可补

```text
native: 今天气很好
vlm:    今天天气很好
```

VLM 多出的 `天` 被稳定上下文夹住，可判定为 `NATIVE_MISSING`。在满足阈值时输出：

```text
今天天气很好
```

### native 顺序错，VLM 顺序可参考

```text
native_geo_text:       A C B D
native_vlm_order_text: A B C D
vlm_text:              A B C D
```

如果重排后锚点覆盖率高、冲突率低、分数提升明显，则输出 native 字符重排后的结果：

```text
A B C D
```
